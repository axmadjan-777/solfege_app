# Работа с учебной программой

Навигация по требованиям и порядок изменения учебных данных. Текущее устройство
загрузки описано в [architecture.md](../architecture.md), задачи и граница
ближайшего релиза — в [roadmap](../product_roadmap.md). Этот файл не запускает
разработку уроков и не заменяет методическую спецификацию.

## Где искать требования

[spec.md](spec.md) — импортированная программа: методика, карточки уроков,
параметры тренажёров и исходные JSON. Она описывает требования, включая будущие
возможности. Название части 4 «Архитектура приложения» относится к учебному замыслу,
а не к проверенной карте текущего кода.

Ищи заголовок или ID и читай нужный фрагмент:

```bash
rg -n '^# Часть |^### PR-|^### L00-01\.' docs/curriculum/spec.md
```

| Задача | Части спецификации |
|---|---|
| Звук и скрытие нот до ответа | 5 |
| Прогресс, повторение и пороги | 6 и 9 |
| Один тренажёр | Его карточка в 8, параметры в JSON |
| Один урок | Его карточка в 11, объект в JSON |
| Состав исходного MVP | 10; расхождения с реализацией — APP-03 roadmap |
| Методический вопрос | 2 и 16 |
| Схемы данных | 17–20 и [schemas](schemas/) |
| Целостность | 27 и [test/curriculum](../../test/curriculum/) |

Для просмотра данных выбирай объект из извлечённого файла вместо загрузки
всех частей 21–26:

```bash
jq '.practice_sets[] | select(.id=="PR-01")' assets/curriculum/exercises.json
jq '.lessons[] | select(.id=="L04-11")' assets/curriculum/lessons.json
jq '.config.mastery_rules, .config.review_policies' assets/curriculum/levels.json
```

## Как обновлять данные

Канонический источник [extract_curriculum.py](../../tool/extract_curriculum.py) —
именованные JSON-блоки в `spec.md`. [Assets](../../assets/curriculum/) и
[схемы](schemas/) — извлечённые копии. Изменение только копии не проходит проверку.

Если задача разрешает изменение содержания или схемы:

1. Исправь нужный исходный JSON-блок в `spec.md` и связанную прозу.
2. Запусти `python3 tool/extract_curriculum.py`.
3. Проверь diff всех копий, затем `python3 tool/extract_curriculum.py --check`
   и затронутые тесты целостности.

В части 15 спецификации описан прежний внешний конвейер `data/parts` и
`docs/solfeggio-app-program/`. В этом репозитории его нет; здесь действует порядок
выше. UI- или документационная задача сама по себе не требует менять данные.

При расхождении прозы и JSON назови обе стороны: структуру и параметры бери из
JSON, методическое намерение — из карточки. Продуктовое противоречие, меняющее
приёмку, нужно разрешить в рамках задачи, а не скрыть изменением порога.
Прежние исключения и допущения сохранены в разделах 3 и 7
[архива I0–I25](../archive/mvp-implementation-plan.md); их актуальность проверяй
по требованиям и коду, не считай разрешением на новые изменения.

## Что учитывать при реализации

- Пользовательские строки — по-русски, идентификаторы кода — по-английски.
  Используй существующие `title`, `feedback` и `SolfegeNotes`: си = B.
- Сохраняй различие немедленного успеха и отложенного `mastered` из части 6.
  Связь прогресса с доступом проверяй через оболочку, не только экран с фейковым
  `isMastered`.
- Численные пороги, диапазоны MIDI, стадии, `mvp_status` и интервалы повторения
  бери из данных. Здесь их копий нет; не ослабляй требования ради зелёного теста.
- Логику генерации, проверки ответа и прогресса держи отдельно от UI. Используй
  существующие `ProgressStore`, `PracticeAudioPlayer`, часы и seed.

## Какие проверки выбрать

| Что меняется | Что подтверждает результат |
|---|---|
| Контент | Модели, ссылки, графы и границы MVP в `test/curriculum/` |
| Правила | Логика с фиксированными временем и seed в `test/practice/`, `test/theory/` |
| Экран | Ответ → обратная связь → запись результата, с фейковым звуком |
| Доступ и сохранение | Реальная точка входа → урок/тренажёр → сохранение → повторное открытие; для аккаунтов — смена пользователя |

Общий QA, живые проверки и завершение задачи регулирует [AGENTS.md](../../AGENTS.md).
Проверка наличия карточек или файлов не означает приёмку учебного пути.
