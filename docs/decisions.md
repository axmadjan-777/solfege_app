# Журнал существенных решений

Хранит причины выбора, альтернативы и последствия. Текущее устройство — в
[architecture.md](architecture.md), исполняемые правила — в [AGENTS.md](../AGENTS.md),
очередь работы — в [roadmap](product_roadmap.md). Записи не заменяют эти документы.

## Когда нужна запись

Добавляй запись при выборе, который влияет на хранение, внешние зависимости,
границы системы, совместимость данных или общий процесс разработки. Не записывай
сюда каждую правку, результат теста или пересказ сессии: это остаётся в PR.
Не придумывай задним числом причины существующего кода.

Формат: постоянный ID и название, дата, статус, контекст, выбранное решение,
альтернативы, последствия, ссылка на основание. Статусы: **предложено**,
**принято**, **заменено**. Принятое решение может ещё ожидать внедрения в `main`:
это указывается отдельно со ссылкой на PR. При пересмотре сохрани прежнюю запись,
отметь её заменённой и добавь ссылку на новую; номера не переиспользуй.

Пока записи короткие, достаточно одного файла. Если решения станут объёмными,
их можно вынести в `docs/decisions/` по одному ID, сохранив здесь указатель.

## D-001. Разделить документацию по назначению

**Дата:** 2026-11-04. **Статус:** принято в рамках задачи на документацию.
**Внедрение:** [PR #14](https://github.com/axmadjan-777/solfege_app/pull/14).
Актуальные статус слияния и коммит внедрения указаны в PR.

**Контекст.** Правила цикла повторялись в AGENTS и промпте, описание приложения —
в README и roadmap. При изменении требовалось обновлять несколько текстов.
Исторический план находился рядом с рабочим промптом.

**Решение.** У каждого вида сведений один основной документ; распределение и
условия обновления собраны в [карте README](../README.md#documentation-map).
Постоянные инструкции ведут к нужному контексту по задаче. Архив отделён от
действующих документов, а история выполненных изменений остаётся в Git и PR.

**Альтернативы.** Один большой AGENTS снова смешивал бы правила, факты и историю.
Набор STATE/MEMORY/SESSIONS добавил бы пересекающиеся записи без отдельного
читателя. Полный шаблон архитектуры из множества файлов пока избыточен.

**Последствия.** Читать нужно меньше нерелевантного текста, но при переносах
необходимо проверять ссылки. Краткая навигационная сводка допустима; подробное
правило или статус не поддерживаются в нескольких местах.

**Основание.** Поручение разделить контекст документов; использованы принципы
[Diátaxis](https://diataxis.fr/) и
[контекстного чтения AGENTS.md](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra).
Это выбранная структура проекта, а не обязательный набор файлов инструмента.

## D-002. Проверять один состав QA локально, перед коммитом и в CI

**Дата:** 2026-11-04. **Статус:** принято в рамках задачи на харнесс.
**Внедрение:** [PR #14](https://github.com/axmadjan-777/solfege_app/pull/14).
Актуальные статус слияния и коммит внедрения указаны в PR.

**Контекст.** Незастейдженная правка могла скрыть ошибку подготовленного коммита,
а разные SDK и составы локальных/серверных проверок давали несопоставимые результаты.

**Решение.** Общий исполняемый список — [tool/verify.sh](../tool/verify.sh),
версии — [tool/toolchain.env](../tool/toolchain.env). Pre-commit проверяет снимок
индекса отдельно от рабочей копии; CI вызывает тот же список. Команды и ограничения
поддерживаются в README, порядок завершения задачи — в AGENTS.

**Альтернативы.** Проверка только рабочего каталога не подтверждает состав коммита.
Отдельные списки команд в hook и CI могут разойтись. Только локальный hook не
обеспечивает обязательную проверку на GitHub.

**Последствия.** Коммит занимает несколько минут; hook нужно подключать в каждой
копии. Такой QA проверяет код и сборку с подменой внешних сервисов. Он не является
вторым ИИ-ревьюером или stop hook завершения ответа агента. Защита `main`
настраивается отдельно в GitHub; её состояние отражено в OPS-01 roadmap.
Живые пользовательские сценарии остаются отдельной задачей приёмки.

**Основание.** Поручение настроить QA перед коммитом и на GitHub; реализация в PR #14.

## О формате журнала

Используется сокращённый формат ADR: контекст → решение → статус → последствия.
Подход описан у [Michael Nygard](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)
и в [arc42](https://docs.arc42.org/section-9/). Изменение требований или приоритета
задачи само по себе не требует новой записи.
