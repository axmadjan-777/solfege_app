# Сольфеджио

Flutter-приложение для обучения музыке: теория, тренировка слуха и музыкальный
ИИ-помощник. Этот README помогает настроить, запустить и проверить проект.
Описание работающего кода — в [architecture.md](docs/architecture.md),
задачи и границы приёмки — в [roadmap](docs/product_roadmap.md).

## Требования и SDK

- Точные версии **Flutter и Deno** — в [tool/toolchain.env](tool/toolchain.env).
  Flutter закреплён по успешному [CI-прогону](https://github.com/axmadjan-777/solfege_app/actions/runs/37341857670).
- Git, Bash, Python 3, Node.js 24 (не ниже 24.3) и npm. Chromium закреплён
  версией Playwright в `tool/browser/package-lock.json`.
- `environment.sdk` в `pubspec.yaml` задаёт диапазон **Dart**, не версию Flutter.
  Используйте закреплённый Flutter, совместимый с существующим `pubspec.lock`.
- Android/iOS SDK нужны только для соответствующих сборок, не для основного QA.

Установите указанные версии из [Flutter SDK](https://docs.flutter.dev/install/archive)
и [Deno releases](https://github.com/denoland/deno/releases). Общий
[выбор SDK](tool/toolchain.sh) использует явно заданные `FLUTTER_BIN`/`DENO_BIN`,
затем локальные версии в `$HOME/.local/share/solfege_app/toolchains/`, затем PATH
и резервные `$HOME/flutter/bin/flutter`, `$HOME/.deno/bin/deno`.
В локальном каталоге ожидаются `flutter-<версия>/bin/flutter` и
`deno-<версия>/deno`; его можно переопределить через `SOLFEGE_TOOLCHAIN_DIR`.
Харнесс не устанавливает и не обновляет SDK самостоятельно.

```bash
source tool/toolchain.sh
"$FLUTTER_BIN" pub get --enforce-lockfile
bash tool/install_hooks.sh
bash tool/verify.sh
```

Для нестандартного пути передайте, например, `FLUTTER_BIN=/path/to/flutter/bin/flutter`.
Для IDE отдельно выберите тот же SDK. Обновление зависимостей — отдельное
согласованное изменение; обычная проверка не переписывает `pubspec.lock`.

## Запуск приложения

Один раз создайте локальную конфигурацию:

```bash
cp dart_defines.example.json dart_defines.json
# Вставьте publishable / anon key из Supabase Dashboard → Project Settings → API
./run_web.sh
```

Не заменяйте уже настроенный файл шаблоном. Он исключён из Git. `service_role`
и Gemini API key нельзя передавать во Flutter или включать в web-сборку.
Перед инициализацией клиент принимает только publishable / anon key; секретный
ключ или токен управления показывает ошибку конфигурации и блокирует подключение.

Другие способы запуска после выбора SDK:

```bash
source tool/toolchain.sh
"$FLUTTER_BIN" run -d chrome --dart-define-from-file=dart_defines.json
```

В Cursor/VS Code есть конфигурации в [.vscode/launch.json](.vscode/launch.json).
Без ключей приложение показывает «Supabase не настроен». Это ожидаемо для
проверки запуска, но не открывает основной интерфейс.

После изменения `dart_defines.json` полностью перезапустите приложение:
hot reload не перечитывает `--dart-define`. В zsh не оставляйте пустую строку
после завершающего строку `\`. Остановка — `q`/Ctrl+C в терминале запуска или
`./stop_web.sh`; скрипт посылает SIGTERM только Flutter web-серверу с рабочим
каталогом этой копии, не всем копиям проекта на машине.

## Supabase и Gemini

Базовая конфигурация проекта — [supabase/config.toml](supabase/config.toml),
схема профиля и RLS — [supabase/schema.sql](supabase/schema.sql).
Настройка живого проекта и применение SQL — отдельная операция с разрешением,
не часть `verify.sh` или установки hooks. Состояние файлов не доказывает,
что та же схема уже применена на сервере.

Для нового окружения:

1. Примените схему профиля к выбранной тестовой БД. Триггер создаёт профиль
   при регистрации; onboarding-поля допускают `null`, затем заполняются upsert.
2. Включите Email provider и настройте confirmation/reset письма. Для реальных
   пользователей настройте SMTP; текущие лимиты проверяйте в панели Supabase.
3. Для существующего production-сайта Site URL —
   `https://axmadjan-777.github.io/solfege_app/`, Redirect URLs включают
   `https://axmadjan-777.github.io/solfege_app/**`. Для другого окружения проверьте
   также redirect URL в клиенте. Не меняйте общую production-настройку ради теста.
4. Сохраните publishable / anon key в локальном `dart_defines.json`.

Телефонный вход отключён в интерфейсе; Phone provider для текущего сценария
не нужен. Apple Sign-In требует отдельной настройки Apple Developer и provider
в Supabase; секрет Apple остаётся на сервере.

Ссылки подтверждения и сброса пароля проверяйте на тестовом аккаунте:
офлайн-тесты не подтверждают доставку писем. Устройство auth-сценария — в
[architecture.md](docs/architecture.md).

Для ИИ серверу нужен `GEMINI_API_KEY` в Edge Functions Secrets. Значение
`GEMINI_MODEL` переопределяет модель; дефолт в коде — `gemini-3.1-flash-lite`.
Доступность модели и квоты конкретного проекта требуют живой проверки.
Развёртывание функции, когда оно входит в задачу:

```bash
supabase functions deploy gemini-chat --project-ref zehmcszijutthmeswtci
```

## QA и pre-commit

Общий QA — автоматические проверки из [tool/verify.sh](tool/verify.sh), без
вызова ИИ-ревьюера. Карта тестов, ограничения покрытия, порядок приёмки фичи
и правила обновления этой карты — в [testing.md](docs/testing.md).

Полная команда — `bash tool/verify.sh`. Она проверяет документацию, версии SDK и выполняет:

1. Python-тесты инструментов разработки; проверки Git-хука используют временные репозитории.
2. `flutter pub get --enforce-lockfile` и анализ без повторного `pub get`.
3. Сверку JSON с исходными блоками спецификации.
4. Все Flutter unit/widget-тесты.
5. Одну проверку типов Edge Function, live-харнесса и Deno-тестов, затем офлайн-тесты
   с подменёнными Auth/Gemini, без повторной проверки типов, сетевых и env-разрешений Deno.
6. `npm ci` по lock-файлу, проверку TypeScript и одну release-сборку реального
   приложения через QA entry point с включённой Semantics, без production-ключей.
7. Сквозные Playwright-сценарии в Chromium, мобильный и настольный viewport,
   сравнение скриншотов. В этом наборе подменён только HTTP внешних сервисов.

Перед первым полным QA установите закреплённый Chromium явно:

```bash
npm ci --prefix tool/browser --ignore-scripts
(cd tool/browser && npx --no-install playwright install chromium)
```

На Linux для системных зависимостей используйте `playwright install --with-deps chromium`.
Изолированный браузерный прогон: `bash tool/verify_browser.sh`.
Команда `--optimization-level=1` пригодна для локальной отладки; приёмка и CI
используют значение по умолчанию 4. `--reuse-build` проверяет хэши исходников,
сборки и конфигурации перед повторным использованием готового bundle.

Любая ошибка останавливает пайплайн. QA не изменяет исходники; кэши и сборка
могут появляться в игнорируемых каталогах. Настоящие Auth/RLS/Gemini проверяются
отдельно через `bash tool/verify_live.sh` и
`bash tool/verify_browser.sh --live --reuse-build`; настройка и границы — в
[testing.md](docs/testing.md#живые-сервисы). Реальная слышимость требует проверки
человеком на целевом устройстве. Отдельное модельное ревью выполняется по
[AGENTS.md](AGENTS.md#отдельное-ии-ревью-перед-итоговым-коммитом-и-готовностью-pr).

Для изменений только `README.md` и Markdown в `docs/`, кроме всего
`docs/curriculum/` и любых `AGENTS.md`, используется лёгкий режим:
`bash tool/verify.sh --docs-only`. Он проверяет UTF-8, маркеры конфликтов и
существование локальных путей встроенных Markdown-ссылок в обычной документации и AGENTS.
Якоря внутри файлов и внешние сайты не проверяются. Flutter/Deno и сборка не нужны.
Пробельные ошибки проверяются через `git diff --check` в CI и pre-commit
(без коммита выполните его вручную).

Общий классификатор [qa_scope.py](tool/qa_scope.py) выбирает режим по всем
изменённым путям, включая удаления и обе стороны переименований. Учебная
спецификация, схемы, данные, код, тесты, конфигурация, `AGENTS.md` и сам харнесс
всегда требуют полного QA. Смешанные изменения, пустой список и неизвестная
база сравнения также проверяются полностью. Все прежние тесты остаются в полном QA.

Подключение один раз **в каждой рабочей копии**:

```bash
bash tool/install_hooks.sh
```

Установщик задаёт локальный `core.hooksPath=.githooks` и не заменяет чужие hooks.
[Pre-commit](.githooks/pre-commit) вызывает [qa_staged.sh](tool/qa_staged.sh):
снимок индекса распаковывается во временный каталог, там выбирается и запускается
режим QA по сравнению с HEAD. Первый коммит всегда проверяется полностью.
Незастейдженные правки и локальные секреты туда не попадают. При ошибке или
изменении индекса во время проверки коммит блокируется; временная копия удаляется.
Для ручного запуска той же проверки: `bash tool/qa_staged.sh`.
Проверка может занять несколько минут.

Хук срабатывает перед **коммитом**, а не на завершение любого ответа агента.
При разрешённом коммите итоговый прогон выполняет hook; повторять его вручную
перед коммитом не нужно. Без коммита агент выбирает проверку по AGENTS.md.
Git позволяет обойти локальный hook; независимая проверка в CI остаётся необходимой.

## CI и публикация

[Verify](.github/workflows/verify.yml) запускает `verify`, затем `live-acceptance`
на PR и при его обновлении. Для документации второй job сообщает `not_required`;
для полного изменения требует настоящие сервисы. Отдельного запуска на push ветки нет.
Режим определяется по полному diff базы PR и проверяемого merge-коммита.
Даже для документации job выполняется и возвращает статус: фильтры
`paths-ignore` и пропуск всего workflow не используются. Конфликт с `main`
нужно разрешить, прежде чем GitHub сможет проверить merge-коммит PR.

[Deploy Flutter Web](.github/workflows/deploy_web.yml) для `main` сначала вызывает
тот же Verify один раз, затем собирает сайт с GitHub secrets `SUPABASE_URL` и
`SUPABASE_PUBLISHABLE_KEY` и публикует Pages. Ручной deploy также ограничен `main`.
Проверка без ключей и production-сборка относятся к одному коммиту.
Для push в `main` режим выбирается по diff предыдущего и нового коммита;
лёгкий QA документации не отменяет production-сборку перед публикацией.
Ручной Verify или deploy выполняет полный QA. В обычном цикле есть один набор
на PR и один перед публикацией `main`. Отменяются только устаревшие офлайн jobs;
живой набор сериализован и завершается с восстановлением тестовых профилей.
Публикация проверяет актуальность SHA `main`, использует уникальное имя Pages
artifact и после deploy проверяет HTTP 200. Это не повторяет живую приёмку.
Независимый CI не заменяется локальным hook.

Живой job использует repository secrets `QA_PROJECT_REF`, `QA_SUPABASE_URL`,
`QA_SUPABASE_PUBLISHABLE_KEY` и `QA_USER_A_EMAIL`, `QA_USER_A_PASSWORD`,
`QA_USER_A_ID` (аналогично для B). `QA_LIVE=1` задаётся явно. Fork/untrusted PR
блокируется до доступа к секретам. Используются только выделенные аккаунты;
service-role ключ, SQL и изменение настроек проекта не нужны.

Workflow не включает защиту `main` автоматически. Обязательный успешный
checks `verify` и `live-acceptance` перед merge задаются отдельно в GitHub branch
rules; при настройке сверяйте точное имя и источник checks на текущем PR.
Состояние этой работы — OPS-01 в [roadmap](docs/product_roadmap.md).

## Проверка на телефоне

Выберите закреплённый SDK, подключите устройство и проверьте `flutter devices`.
Запускайте с `--dart-define-from-file=dart_defines.json`. Отдельно проверьте звук,
авторизацию и возвращение по email-ссылке: в мобильном приложении ссылка может
открыться в браузере. Эти сценарии не входят в web-сборку харнесса.
