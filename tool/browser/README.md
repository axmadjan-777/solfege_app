# Browser acceptance and screenshots

The runner builds `test_driver/qa_main.dart`, which enables Flutter Semantics and
calls the real application `main`. It uses the production AuthGate, services,
shell, lesson/practice routes, progress rules and SharedPreferences Web storage.
Only the Auth, profiles and Edge Function HTTP responses at `https://qa.invalid`
are fixtures. Unknown external requests fail the test. No credentials or live
Supabase project are needed.

Install the lockfile dependencies and pinned Chromium explicitly:

```bash
npm --prefix tool/browser ci --ignore-scripts
(cd tool/browser && npx playwright install chromium)
```

On a fresh Linux machine, use `npx playwright install --with-deps chromium` in
that explicit setup step. The ordinary runner never installs a browser or SDK.
It selects the project's Flutter SDK through `tool/toolchain.sh`, checks the
version, builds the QA target, starts a loopback server and stops that server on
completion or interruption. Acceptance uses release optimization level 4.
`--optimization-level=1` is available explicitly for faster local iteration;
the level is recorded in the Playwright report metadata and
`build/browser-run.json`.

Run both viewport projects from the repository root:

```bash
bash tool/verify_browser.sh
bash tool/verify_browser.sh --project=chromium-mobile
```

`QA_BROWSER_PORT` can select another loopback port. The default is 8765.

The scenarios cover onboarding and pending registration, a reload before email
confirmation, a normal implicit email link, profile creation and entry into the
shell. The fresh account completes all eight guided coach steps through the
actual highlighted controls, then follows the open first lesson without any
gate override, enters its separate control practice, verifies the early wait,
restores a new browser context, passes a 4-answer cold review after 21 browser
hours and opens L00-02 and its linked daily mix. Each control/cold answer requires
the real WAV Blob playback to finish; the player and sound are not mocked.
The returning-account route uses
L03-04 → PR-08, saves actual attempts, checks
the early cold-review rejection and mastery after 21 browser hours, opens the
next lesson from the shell, reloads, recreates the browser context from real
storage and switches A → B → A. It also types a chat question through the real
composer and checks the exact accessible/rendered message from the HTTP fixture;
its screenshot is separate from the genuine service check below. The recovery
scenario opens an implicit recovery link, reloads the pending form, saves a new
password through AuthService and verifies the shell again after reload.

Only that linked scenario seeds a prerequisite: `not.anchors_treble`. Its JSON
was generated by production `MemoryProgressStore.recordSession` and
`ProgressBook.toJson`, with 12 correct training answers and a later 4-answer cold
review. No target competency is seeded and no `isMastered` callback is replaced.
Regenerate the fixture deliberately after a relevant serialization/rules change:

```bash
source tool/toolchain.sh
"$FLUTTER_BIN" test tool/browser/generate_progress_fixture.dart
```

Screenshots use pinned Playwright/Chromium, 390×844 and 1440×1000 viewports,
DPR 1, Russian locale, UTC, fixed dates/data, light mode, reduced motion and
settled Flutter transitions. Baselines live in `snapshots/darwin/` and
`snapshots/linux/`; generate and review each on its real operating system.
Ordinary tests use `updateSnapshots: 'none'` and fail on missing baselines.
Create or replace baselines only with the explicit command:

```bash
bash tool/verify_browser.sh --update-snapshots
```

Review the new PNGs before accepting their diff. Never copy macOS PNGs into the
Linux directory. The update command explicitly uses Playwright's `all` mode;
comparison uses zero differing pixels and a zero color threshold, so small
background changes are also checked. Playwright writes failed screenshot expected/actual/diff PNGs,
failure screenshots, traces, persisted fixture storage and JUnit results into
`build/browser-results/`. The HTML report is `build/browser-report/`, and server
output is `build/browser-server.log`.

The chat screenshot holds the HTTP fixture until Send is visibly disabled,
then releases the reply and explicitly moves keyboard focus from the composer
to the re-enabled Send button. This makes its focus overlay stable regardless
of whether a fast response would have coalesced the loading frame. The two
offline viewport projects may run in parallel; cases within each project stay
sequential. Live execution always uses one worker.

The pinned Flutter engine downloads its default Roboto even with local
CanvasKit. `prepare_web.py` sets `fontFallbackBaseUrl` in the generated bootstrap
and serves the exact engine-default WOFF2 locally. This changes only the QA
build output. Source:
[engine-default Roboto WOFF2](https://fonts.gstatic.com/s/roboto/v32/KFOmCnqEu92Fr1Me4GZLCzYlKw.woff2)
(the URL in Flutter 3.47.6 `engine/canvaskit/fonts.dart`). `fonts/SHA256SUMS`
verifies its bytes; the Apache license is included. Fonts are not downloaded
during verification.

These checks verify browser behavior with HTTP fixtures. They do not establish
real email delivery, RLS, audible output, or a live model response.

## Live UI against the same bundle

The opt-in command is:

```bash
bash tool/verify_browser.sh --live --reuse-build
```

The caller explicitly sets `QA_LIVE=1`, `QA_PROJECT_REF` (matching the exact URL
host), `QA_SUPABASE_URL`, `QA_SUPABASE_PUBLISHABLE_KEY`, and
`QA_USER_A_EMAIL`, `QA_USER_A_PASSWORD`, `QA_USER_A_ID` (and the corresponding B
settings) through the process environment. The runner does not read a secret
file. A/B UUIDs and emails must be distinct. Only dedicated, already-confirmed QA accounts with their own complete
profiles are supported. This command signs in A, verifies its real profile,
enters a music question through the UI, receives and displays an actual Gemini
answer, signs out, and checks B's own profile and initial progress.

The compiled bundle still contains only `https://qa.invalid` and the public
fixture key. A transparent Playwright HTTP proxy forwards the permitted Auth,
profile reads and `gemini-chat` calls to the configured project with its client
key, then fulfills the original request using the real response. It does not
invent response bodies or session data. There are no registration, email,
password-reset or profile-write endpoints in the live proxy allowlist, and no
browser clock override in live mode.

`--reuse-build` makes no Flutter or `pub get` calls. It checks
`build/browser-run.json` against the pinned version, target, optimization level,
`QA_SOURCE_TREE` (or the checkout's HEAD tree), runtime input hashes, and bundle
bytes. Build creation also rejects runtime inputs that changed during
compilation. An isolated staged snapshot supplies `QA_SOURCE_TREE` explicitly.
CI downloads `build/qa-web/` and `build/browser-run.json` from the accepted build
job, using the same source tree. Manifest checks have credential-free Python
tests:

```bash
python3 -m unittest discover -s tool/browser/tests -p 'test_*.py'
```

For a local build with uncommitted changes and no explicit `QA_SOURCE_TREE`, the
`source_tree` value labels the checkout's HEAD base; it does not claim that the
bundle was built from a clean HEAD. `source_inputs_sha256` identifies the actual
runtime files that were compiled, and `bundle_sha256` identifies the resulting
bytes. The staged hook and CI supply the exact staged/checked-out source tree
explicitly. Never replace a bundle's recorded tree with a later index hash.

Live traces, video, HAR, screenshots and persisted storage artifacts are
disabled. A separate reporter ignores raw stdout/stderr, errors, steps and
attachments; it emits only fixed phase names, status, duration and allowlisted
service HTTP status numbers in `build/browser-live-results/results.json`.
Playwright's private failure output is removed by both the reporter and runner
cleanup. No HTML report or pixel baseline is generated for the nondeterministic
live answer. Live execution is separate from ordinary offline acceptance.
