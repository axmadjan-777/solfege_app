# AGENTS.md — правила работы в solfege_app

## Контекст проекта

Приложение для обучения сольфеджио: Flutter-клиент и Supabase Edge Function
для чата с Gemini. Карта модулей и потоков данных — в
[architecture.md](docs/architecture.md). Этот файл хранит постоянные правила
работы агента; задания и текущий статус находятся в других документах.

## Перед началом: что читать

Прочитай этот файл и [pubspec.yaml](pubspec.yaml). Проверь `git status --short`,
ветку, HEAD и remotes; отдели существующие изменения от своей задачи.
Дальше открывай только нужный контекст и прослеживай связанные файлы по импортам:

- Запуск, SDK и публикация — [README](README.md).
- Границы модулей, хранение и связь экранов с сервисами —
  [architecture.md](docs/architecture.md).
- Выбранная задача и критерии приёмки — карточка рабочей доски или
  [roadmap](docs/product_roadmap.md), указанные в поручении.
- Причины существенного решения — относящаяся к задаче запись в
  [decisions.md](docs/decisions.md).
- Теория, практика и учебные данные — [curriculum/README](docs/curriculum/README.md),
  затем нужная часть спецификации по заголовку или ID. Целиком её не загружай.

[Шаблоны запроса и отчёта](docs/task-prompt.md) нужны при постановке задачи
и передаче результата; там же — пример переходов карточки. Архив и локальные
`.cursor/plans/` — исторические материалы, не действующие инструкции.
Не требуй прочитать все документы перед небольшой правкой.

## Как различать факты и требования

Текущее поведение подтверждай кодом проверяемого коммита и воспроизводимым
сценарием. Требуемое поведение определяют задача и относящиеся к ней требования.
При несовпадении назови расхождение; не подменяй требование существующим дефектом.
Реализация в коде и продуктовая приёмка — разные статусы.
Открытый PR не является частью `main`.

## Основные команды

| Для чего | Команда |
|---|---|
| Запустить / остановить web этой копии | `./run_web.sh` / `./stop_web.sh` |
| Проверить код и выбранные сценарии | `./tool/check.sh [all\|answers\|progress]` — [границы и чтение ошибок](README.md#проверки) |
| Извлечь учебные данные из спецификации | `python3 tool/extract_curriculum.py` |

Версия Flutter — в [tool/toolchain.env](tool/toolchain.env); установка и выбор
SDK описаны в README. Обновление SDK и зависимостей выполняй отдельной задачей.

## Цикл одной задачи

1. Зафиксируй результат, область изменений и критерии карточки. Прочитай её
   текущий статус и переведи разрешённую задачу из «Очередь» в «В работе».
2. При исправлении бага воспроизведи его на известной версии: запиши действия,
   ожидаемый и фактический результат. Для значимого бага добавь проверку через
   публичное поведение и убедись, что она падает именно из-за дефекта, а не
   настройки окружения. Для новой фичи так же проверь отсутствие нужного поведения.
3. Внеси минимальное законченное изменение и повтори затронутые проверки.
   Сохрани проверку значимого бага от повторного появления. Не ослабляй ожидания
   и не пропускай проверки ради зелёного результата. Обнови документ, которому
   принадлежит изменившийся факт, по [карте документации](README.md#documentation-map).
4. Перед передачей результата выполни итоговый набор: для кода приложения
   и проверок — полную команду из [README](README.md#проверки) и нужный ручной
   сценарий. Для документации проверь содержание, ссылки и пример; для других
   инструментов — их изменённое поведение. Просмотри итоговый diff и состав
   файлов: соответствие критериям и правилам проекта, отсутствие секретов
   и случайно обновлённого lock-файла.
5. Запиши проверенный коммит и доказательства в карточку по
   [шаблону отчёта](docs/task-prompt.md#отчёт). Переведи её в «Проверка», когда
   результат готов к ревью или приёмке. Заверши разрешённые Git/PR-действия;
   переход в «Готово» определяется условиями ниже.

### Возврат к исправлению

Ошибка проверки или подтверждённое замечание ревью возвращают карточку из
«Проверка» в «В работе». Запиши конкретную причину, исправь её, повтори затронутые
проверки, затем итоговый набор и ревью изменённой версии. При неизменном успешном
результате повторный прогон без новой причины не нужен.

Если та же ошибка повторяется без новых данных, останови слепые попытки:
запиши в карточке причину блокировки, уже проверенные гипотезы и следующее
наблюдение для диагностики. Карточка остаётся «В работе» с указанием блокировки;
продолжай с новой гипотезы или после изменения окружения.

### Когда задача готова

«Готово» требует выполненных критериев карточки, успешных относящихся проверок
на итоговой версии, необходимого ручного сценария и отсутствия открытых
блокирующих замечаний. В карточке должны быть ссылка на результат, проверенный
коммит и отдельно — что не проверялось и почему. Если результат должен попасть
в `main`, открытый PR остаётся в «Проверка» до разрешённого слияния.

Сбой окружения, недоступный сервис и непроверенное поведение отмечай как
«заблокировано» или «не проверено», а не PASS. Обязательный критерий с таким
результатом не позволяет завершить задачу; сценарий вне согласованного объёма
укажи как ограничение. Для документации или иной задачи без пользовательского
сценария явно запиши, почему ручная проверка приложения не требуется.

## Границы задачи и данных

Выполняй текущее поручение до результата. Roadmap, архив и обнаруженные дефекты
не разрешают автоматически начинать следующие задачи. «Продолжай» относится
к незавершённой согласованной работе. При аудите только читай; при задаче на
документацию или инструменты разработки не меняй приложение. Обычные обратимые решения внутри
задачи принимай самостоятельно, с учётом уже полученных разрешений пользователя.

Не печатай ключи и не коммить `dart_defines.json`. `service_role` и
`GEMINI_API_KEY` остаются на сервере. Живые SQL, письма, настройки Supabase и
деплой изменяй только в разрешённой задаче. Изменение подтверждения email в общем проекте требует отдельного поручения. Учебные JSON меняй по curriculum/README.

## Git и PR

Проверяй актуальные ветку и PR; не закрепляй их имена в постоянных инструкциях.
После merge новую задачу начинай от актуального `main`, по умолчанию
`codex/<короткое-имя>`. Один PR — одна связная задача.

Коммит/push выполняй в разрешённом объёме после просмотра diff. Добавляй
конкретные пути, не `git add -A`. Не затирай чужие правки и не переписывай чужие
коммиты. Force-push, merge и удаление веток требуют разрешения на эти действия.
Используй доступный GitHub-инструмент без привязки к API конкретного агента.

## Поддержка документации

У каждого документа одна основная роль и условие обновления в карте README.
Обновляй его вместе с изменением, которое сделало текст неверным. На общий факт
ссылайся вместо копирования подробностей; краткие указатели допустимы.
Не обновляй дату сверки без проверки и не добавляй ежедневные отчёты в постоянные
инструкции. Для истории выполненной задачи достаточно PR и Git.
Дублировать AGENTS.md в `.cursor/rules` не нужно.
